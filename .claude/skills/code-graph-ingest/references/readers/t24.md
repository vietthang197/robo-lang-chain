# Reader profile: `t24`

Đọc repo Temenos T24 (core banking) và map vào **cùng mô hình chuẩn** với Spring (`../schema.md`), để T24 hiện đúng trong topology và lời gọi OFS từ service khác khớp được vào T24. Repo T24 thường có đủ bốn loại artifact:
1. routine jBC/InfoBasic trong thư mục BP;
2. record export: VERSION, ENQUIRY, APPLICATION/STANDARD.SELECTION, LOCAL.TABLE/LOCAL.REF, EB.API, PGM.FILE;
3. cấu hình tích hợp: OFS.SOURCE, IF.INTEGRATION.FLOW/IF event, IRIS (REST provider), TSA.SERVICE/BATCH;
4. TAFJ Java extension (đọc bằng `java-generic.md`, **cùng projectKey**).

Ví dụ chạy được: `templates/fixtures/t24/` (VERSION `FUNDS.TRANSFER,ACTR` có INPUT.ROUTINE, routine có `GOSUB`/`CALL`/`F.READ`/`F.WRITE`, một ENQUIRY, một OFS.SOURCE).

> **Giả định về định dạng export (cần kiểm chứng trên repo thật).** Định dạng record export của repo thật chưa được xác nhận (DL.DEFINE, file text, XML của Design Studio…). Profile này giả định **mỗi record là một file text** `records/<LOẠI RECORD>/<@ID>.txt`, mỗi dòng một giá trị dạng `FIELD.NAME = value`, field multi-value ghi `FIELD.NAME[n] = value` (n bắt đầu từ 1), dòng đầu `@ID = <id>`. Đây là định dạng của fixture, **to be verified on the real repo**.
>
> **Nếu repo thật khác định dạng này:** không đoán vị trí field. Với mỗi nhóm record không đọc được chắc chắn tên field (ví dụ record dạng mảng giá trị ngăn bởi `FM`/`VM` mà không có tên field, file nhị phân, XML lạ):
> - không tạo node từ các record đó;
> - ghi Gap `unread-files` (askWho=`Dev`, hash trên uid Module chứa chúng, hoặc uid Service nếu chưa có Module) với câu hỏi mô tả **điều đã quan sát được**: đường dẫn, phần mở rộng, 3–5 dòng đầu đã bỏ giá trị secret, ví dụ *"Record VERSION trong `DL/VERSION/*.d` là XML có thẻ `<field name=…>`; field hook nằm ở thẻ nào? Cho biết định dạng export để cập nhật profile t24."*;
> - thêm `diagnostics` mức `warn` và đưa các file đó vào `coverage.skipped` với lý do `export format chưa hỗ trợ`.
>
> Khi đã biết định dạng thật, sửa mục 2 và mục 4 của profile này cùng fixture, rồi chạy lại test (`../../scripts/test/profile-t24.test.mjs`).

### Quy ước cần xác minh trên repo thật

Các quy ước dưới đây do profile tự đặt (chưa có repo T24 thật để đối chiếu); được chấp nhận tạm thời (ruling R21) và **phải kiểm chứng** khi chạy trên repo thật. Nếu repo thật cho thấy quy ước không hợp, sửa profile + fixture + test cùng lúc, không sửa lẻ trong bundle.
1. **Định dạng export record**: một file text mỗi record, `FIELD = value`, multi-value `FIELD[n] = value`, dòng đầu `@ID = …` (đoạn giả định ở trên).
2. **Operation `#ofs`** (`kind=ofs-entry`) cho mỗi VERSION/ENQUIRY: điểm vào OFS giả lập, `EXPOSES` Endpoint ofs (§3, §4.1).
3. **Tiền tố loại record trong qualifiedName** của Component record: `VERSION/APP,NAME`, `ENQUIRY/NAME`, `APPLICATION/APP`.
4. **Operation entry của routine** là `<ROUTINE>#<ROUTINE>`; paragraph là `<ROUTINE>#<LABEL>`.
5. **Key ConfigKey của OFS.SOURCE**: `OFS.SOURCE/<ID>/<FIELD>` (multi-value `…/<FIELD>[n]`).
6. **Che cả user kỹ thuật** `GENERIC.USER` của OFS.SOURCE (ngoài mật khẩu); tên field mật khẩu `GENERIC.PASSWORD` trong fixture là giả, field thật có thể khác.
7. **Module theo product** với thứ tự nguồn PGM.FILE → bảng APPLICATION core → tiền tố routine → thư mục BP (§3).
8. **Routine core Temenos** ghi `ext:t24:<ROUTINE>`/`ext:t24:<ROUTINE>#<ROUTINE>`, chỉ cho lời gọi có ý nghĩa nghiệp vụ (§4.5).

## 1. Detection

Khớp khi có **ít nhất một** trong các dấu hiệu sau (Glob/Grep từ gốc repo):
1. Thư mục routine: tên `BP`, `*.BP` hoặc `*BP` (Glob `**/BP/*`, `**/*.BP/*`, `**/*BP/*`) chứa file không có phần mở rộng (hoặc `.b`, `.jbc`) mà dòng code đầu tiên (bỏ dòng chú thích `*`/`!`/`REM`) khớp `^\s*(SUBROUTINE|PROGRAM|FUNCTION)\s+[A-Z0-9.$_]+` (Grep `^\s*SUBROUTINE ` không phân biệt hoa thường).
2. File chứa `$INSERT I_COMMON` / `$INSERT I_EQUATE` (hoặc `$INCLUDE`, `INCLUDE`).
3. Record export: thư mục mang tên loại record (`VERSION`, `ENQUIRY`, `STANDARD.SELECTION`, `LOCAL.TABLE`, `LOCAL.REF.TABLE`, `EB.API`, `PGM.FILE`, `OFS.SOURCE`, `IF.INTEGRATION.FLOW`, `TSA.SERVICE`, `BATCH`), hoặc file text có dòng `@ID = …` (định dạng giả định ở trên), hoặc gói `DL.DEFINE`.
4. Cấu hình TAFJ: `tafj.properties`, thư mục `conf/` của TAFJ, file `.java` import `com.temenos.*`.

Có file `.java` (dấu hiệu 4) thì áp dụng **thêm** `java-generic` cho phần TAFJ extension, cùng projectKey; ghi cả hai vào `scan.readerProfiles` (`["t24", "java-generic"]`). Fixture chỉ có jBC và record nên `readerProfiles` = `["t24"]`.

Một instance T24 ở một env = **một Service**; projectKey thường là `t24` (fixture: `t24`). Repo chứa nhiều instance (ví dụ core và một T24 riêng cho thẻ) thì **dừng và hỏi người dùng** projectKey cho từng instance.

Chia subagent (repo lớn, > ~40 routine): agent chính đọc toàn bộ record (VERSION, ENQUIRY, EB.API, PGM.FILE, OFS.SOURCE) trước và đưa cho subagent **bảng hook** (routine → VERSION/ENQUIRY + event) và **bảng tên** (EB.API, biến file). Mỗi subagent nhận một product (tiền tố routine `FT.*`, `AC.*`, …) hoặc một thư mục BP, ≤ ~40 routine. Cạnh `CALLS` sang routine của phần khác dùng uid dự kiến theo công thức (mục 3).

## 4. Công thức trích xuất

### 4.1 Endpoint
1. **VERSION** `@ID = APP,NAME` → Endpoint `protocol=ofs`, `httpMethod=null`, `path=null`, `pathRegex=null`, `signature=APP,NAME` (đúng chuỗi `@ID`, giữ dấu phẩy, không khoảng trắng), uid `<env>:<pk>:endpoint:ofs:APP,NAME`; props `application`, `version`. VERSION **không có hook nào vẫn là Endpoint**. Cạnh: `Component(VERSION) -CONTAINS-> Operation(#ofs) -EXPOSES-> Endpoint`, `Deployment -SERVES-> Endpoint`.
2. **ENQUIRY** `@ID = NAME` → Endpoint `protocol=ofs`, `signature=ENQ NAME`, uid `<env>:<pk>:endpoint:ofs:ENQ NAME`; cạnh như VERSION.
3. **OFS.SOURCE** `@ID = ID` → Endpoint kênh OFS tổng `kind=ofs-source`, `signature=OFS.SOURCE ID`, props `ofsSource`; `Deployment -SERVES->`. Không có Operation `EXPOSES` (nguồn OFS chỉ là cổng vào).
4. **IRIS / REST provider** → Endpoint `protocol=iris`, `kind=iris`, `httpMethod`, `path` (path của API, **không** gồm context root của ứng dụng IRIS, giống ruling R16), `pathRegex` sinh từ `path` như `../schema.md` §4, `signature=<METHOD> <path>`, uid `<env>:<pk>:endpoint:iris:<METHOD> <path>` (ví dụ `uat:t24:endpoint:iris:GET /party/customers/{customerId}`). **Ruling R21:** `link` so method + path với Endpoint `protocol=http` **hoặc** `iris` theo cùng quy tắc (host/port/discovery/path, cắt `Deployment.contextPath`), nên lời gọi HTTP (RestTemplate, Feign…) từ service khác khớp được vào IRIS; `SERVICE_DEPENDS_ON.protocol` ghi `iris`. Context root (ví dụ `/irf-provider-container/api`) vào `Deployment.contextPath`. Operation `EXPOSES` là routine/Java xử lý API nếu cấu hình IRIS chỉ ra, không thì không có `EXPOSES`.
5. **TSA.SERVICE / BATCH** → Endpoint `protocol=batch`, `kind=t24-batch`, `signature=<id TSA.SERVICE>`; `TRIGGERS {event:'BATCH.JOB', job:<tên job>}` tới entry routine của từng job trong BATCH.

Ví dụ fixture: `records/VERSION/FUNDS.TRANSFER,ACTR.txt` → `uat:t24:endpoint:ofs:FUNDS.TRANSFER,ACTR`; `records/ENQUIRY/ENQ.CUST.LIST.txt` → `uat:t24:endpoint:ofs:ENQ ENQ.CUST.LIST`; `records/OFS.SOURCE/BROWSERTC.txt` → `uat:t24:endpoint:ofs:OFS.SOURCE BROWSERTC`.

### 4.2 ClientCall
**Phía T24 gọi ra ngoài:**
| Dấu hiệu | clientKind | Trường |
|---|---|---|
| TIF / IF outbound HTTP (cấu hình endpoint URL trong record IF/TIF hoặc `tafj.properties`) | `tif` | `httpMethod`, `urlTemplate` từ cấu hình; base URL từ ConfigKey → `USES_CONFIG {role:'base-url'}` + `resolved*` (`../cross-service.md` §1.2) |
| `CALLJ` tới class Java gọi HTTP (HttpClient, …) | `http-client` (ClientCall gắn vào Operation Java, theo `java-generic.md`) | như trên |
| `CALLJ` tới thư viện ngoài không có source | `callj` | `urlTemplate` = `<FQN>#<method>`, `confidence=medium`; không biết đích → Gap `unresolved-call` |

Gắn vào Operation chứa lời gọi bằng `MAKES_CALL {line}`; uid theo `../schema.md` §2.1 (`<Operation>-><clientKind>:<httpMethod> <urlTemplate>`). Không có lời gọi ra ngoài (như fixture) thì không có ClientCall.

**Phía service khác gọi vào T24 qua OFS** (profile `spring-boot`, BPM… ghi; ghi ở đây để hai phía khớp): message OFS dạng `APP,VERSION/I/PROCESS,<user>/<pass>,<id>,FIELD=…` hoặc `ENQUIRY.SELECT,,<user>/<pass>,NAME,…`:
- `clientKind=ofs`, `httpMethod=null`, `signature` = hai phần trước dấu `/` đầu tiên (`APP,VERSION`, bỏ khoảng trắng), hoặc `ENQ <NAME>` với `ENQUIRY.SELECT`; `urlTemplate` = `signature` (để rule `R5-clientcall-url` thấy URL); uid `…->ofs:FUNDS.TRANSFER,ACTR`.
- **Không bao giờ** chép cả message vào `urlTemplate`/`evidence`/`description`: phần `<user>/<pass>` là credential.
- Message ghép chuỗi lúc chạy (VERSION lấy từ biến/config): `confidence=medium` nếu giải được từ config, không thì `signature=null`, `urlTemplate=null`, uid dùng `?` và Gap `unresolved-call`.
- `link` khớp `signature` với `Endpoint.signature` protocol ofs → `TARGETS {matchedBy:'ofs-version', confidence:'high'}` và `SERVICE_DEPENDS_ON {protocol:'ofs'}` (`../cross-service.md` §2.1 bước 1).

### 4.3 DataStore + mode
- Tên file: tham số đầu của lệnh đọc/ghi là biến `FN.X`; giải bằng phép gán literal gần nhất trong routine (`FN.CUSTOMER = 'F.CUSTOMER'`, thường ở paragraph khởi tạo). Biến lấy từ common block → giải qua insert `I_*` nếu có. Không giải được → Gap `unknown-datastore` (askWho=`Dev`, hash trên uid Operation).
- uid `ds:<env>:t24:F.<APP>`; props `kind=t24-application`, `tech=t24`, `location=F.<APP>`, `name=<APP>`, `application=<APP>`. Hậu tố `$NAU`/`$HIS` (`F.FUNDS.TRANSFER$NAU`) **gộp vào cùng DataStore** `F.FUNDS.TRANSFER`, ghi hậu tố vào props cạnh `ACCESSES {fileSuffix:'$NAU'}`. File có mã công ty (`FBNK.CUSTOMER`, `F.<MNE>.X`) → bỏ phần mnemonic, giữ `F.CUSTOMER`, ghi `props.mnemonic` trên cạnh.
- `ACCESSES` đặt trên **Operation chứa lệnh** (paragraph, không phải entry):
| Lệnh | mode |
|---|---|
| `F.READ`, `CACHE.READ`, `EB.READ*`, `F.MATREAD`, `READ`, `MATREAD`, `SELECT`/`EB.READLIST`/`DAS` | `read` |

### 4.4 Channel
- IF.INTEGRATION.FLOW / IF event (Integration Framework) → `Operation -PUBLISHES-> Channel`. Operation phát là Operation `#ofs` của VERSION/APPLICATION gắn exit point của flow (hoặc routine gọi API phát event). Channel: nếu cấu hình flow ghi rõ topic/queue vận chuyển (Kafka, JMS, MQ) thì dùng đúng tech và tên đó (`ch:<env>:kafka:<topic>`, `ch:<env>:jms:<queue>`) để consumer phía Spring (`@KafkaListener`) khớp được; không thì `ch:<env>:t24-if:<tên flow/event>`.
- DE message (Delivery: `DE.MESSAGE`, `DE.FORMAT.*`, carrier) → `ch:<env>:t24-de:<MESSAGE.TYPE>` (ví dụ `ch:uat:t24-de:103`) với `PUBLISHES` từ Operation phát.
- Node Channel: `props.tech`, `name`. Producer có ClientCall thì `clientKind=<tech>-producer`, `topic` (để `link` khớp `matchedBy:'topic'`). Fixture không có Channel.

### 4.5 CALLS
- `GOSUB L` trong Operation P → `CALLS {dispatch:'gosub', lines:[…], resolved:true}` P → `X#L`. Nhiều `GOSUB` cùng nhãn trong một Operation: một cạnh, gộp `lines`.
- `CALL Y(...)` → `CALLS {dispatch:'call'}` tới `Y#Y`. Tên Y giải qua EB.API khi tên trong record/code khác tên file (§7). Y không có trong repo: là routine core thì xem gạch đầu dòng "Routine core" bên dưới; là routine local thiếu file thì **không** trỏ tới uid project `Y#Y` (cạnh treo, validator báo `R3-dangling`) mà tạo Component/Operation `ext:t24:Y`/`ext:t24:Y#Y` (`external:true`), `CALLS {resolved:false}` tới đó, kèm Gap `unread-files` (askWho=`Dev`, hash trên uid Operation gọi): *"Routine Y được gọi từ X nhưng không có trong repo; nằm ở thư mục/BP nào?"*. (Khi chia subagent, `CALLS` sang routine thuộc phần khác vẫn dùng uid project `Y#Y`; validate sau khi gộp sẽ bắt nếu thiếu.)
- `CALL @VAR` (gọi động) → `CALLS` tới đích đoán được (`resolved:false`) nếu biến gán literal; không thì không ghi cạnh, thêm diagnostics `warn`.
- `CALLJ "<FQN>", "<method>"` → `CALLS {dispatch:'call'}` tới `<env>:<pk>:operation:<FQN>#<method>` (`java-generic.md` §4).
- Routine core (Temenos cung cấp, không có source): **không** ghi CALLS cho tiện ích tầm thường (`OPF`, `STORE.END.ERROR`, `FATAL.ERROR`, `TXT`, `EB.SET.NEW.TASK`, các hàm đọc/ghi file vì đã thành ACCESSES). Ghi `CALLS` tới `ext:t24:<ROUTINE>#<ROUTINE>` (Operation, `external:true`, cùng node `ext:t24:<ROUTINE>` Component) cho lời gọi có ý nghĩa nghiệp vụ: `EB.ACCOUNTING` (hạch toán), `OFS.POST.MESSAGE`/`OFS.BULK.MANAGER`/`OFS.CALL.BULK.MANAGER` (tự gửi OFS), `EB.ROUND.AMOUNT`, `CALCULATE.CHARGE`.
- `lines` là số dòng trong file routine.

Ví dụ fixture: `FT.LOCAL.INPUT#FT.LOCAL.INPUT -CALLS {dispatch:'gosub', lines:[12]}-> FT.LOCAL.INPUT#PROCESS`; `FT.LOCAL.INPUT#PROCESS -CALLS {dispatch:'call', lines:[34]}-> FT.LOCAL.CHECK#FT.LOCAL.CHECK`.
